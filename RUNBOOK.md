# RUNBOOK — как запускать и как понимать, что пошло не так

Четвёртый документ рядом с тремя: `RESULTS.md` — всё измеренное одним местом,
`HANDOFF.md` — состояние и список дел, `RESEARCH_PLAN.md` — что и зачем меряем,
этот — как это запускается на общем узле.

Всё ниже проверено на практике, включая ошибки.

---

## 1. Окружение

Две модели требуют несовместимых версий transformers, поэтому **обе** стоят
отдельными каталогами и подключаются через `PYTHONPATH`. В самом venv лежит
4.51.3 — она не подходит **ни одной** из двух: для 1.5 слишком новая, для 2.0
слишком старая. Раньше здесь было написано, что 1.5 запускается из venv; это
перестало быть правдой после того, как venv обновили.

```bash
export TF20=$HOME/tf457     # transformers 4.57.1
export TF15=$HOME/tf446     # transformers 4.46.3
```

| модель | нужная версия | как запускать |
|---|---|---|
| LLaDA2.0 | ≥4.56 | `bash scripts/llada2.sh <скрипт> ...` либо `PYTHONPATH=$TF20 python ...` |
| LLaDA-1.5 | 4.38–4.46 | `PYTHONPATH=$TF15 python ...` |

Ставится теневой каталог так — torch не подтянется, он transformers не нужен:

```bash
pip install --target=$HOME/tf446 'transformers==4.46.3'
```

Проверка версии стоит **до** импорта модельного кода, поэтому при ошибке в
сообщении сразу написано, что ставить. Она не косметическая: без неё падение
происходит внутри модельного файла чекпойнта на отсутствующем символе.

Обёртка `llada2.sh` подставляет путь, выбирает карту по свободной памяти и
падает с внятным сообщением, если каталога нет. Если `CUDA_VISIBLE_DEVICES`
уже задан снаружи, обёртка его уважает и свой выбор не делает.

Колёса для офлайн-установки: `scripts/make_offline_bundle.py`. pypi с сервера
недоступен, CDN `files.pythonhosted.org` — доступен.

## 2. Выбор карты

**Свободная память и свободный вычислитель — разные вещи.** Карта с 80 ГБ
свободных при загрузке 100% — худший вариант: прогон стартует и ползёт в
тридцать раз медленнее.

```bash
nvidia-smi --query-gpu=index,memory.free,utilization.gpu --format=csv,noheader
```

Годится строка, где памяти больше 34000 MiB **и** утилизация ниже 30%.
Если такой нет — ждать, а не запускать.

**Обёртка и сторожа выбирают только по памяти** — это известный недостаток,
не исправлен.

**Карту могут забрать за те минуты, что прошли между проверкой и запуском.**
Случалось. Для дешёвых замеров надёжнее процессор.

### Когда процессор лучше карты

Скрипты `check_block_cache.py`, `measure_drift.py`, `check_router.py` делают
десятки прогонов на коротких последовательностях. На процессоре это
двадцать-тридцать минут и полная независимость от соседей. Нужно ~32 ГБ
оперативной памяти (`free -g`).

```bash
--device cpu
```

Оценка на GSM8K на процессоре нереальна — там сотни тысяч прогонов.

## 3. Прогоны

### Минуты, карта не нужна

```bash
cd ~/quantization/DLLMQuaRot && nohup bash -c '
set -x
export PYTHONUNBUFFERED=1
PYTHONPATH=$HOME/tf457 python scripts/check_block_cache.py --model inclusionAI/LLaDA2.0-mini --model-type llada2_moe --device cpu
PYTHONPATH=$HOME/tf457 python scripts/measure_drift.py --model inclusionAI/LLaDA2.0-mini --model-type llada2_moe --device cpu
PYTHONPATH=$HOME/tf457 python scripts/check_router.py --model inclusionAI/LLaDA2.0-mini --model-type llada2_moe --device cpu
PYTHONPATH=$HOME/tf446 python scripts/measure_drift.py --model GSAI-ML/LLaDA-1.5 --model-type llada --device cpu
' > out/tier0.log 2>&1 & sleep 2 && tail -f out/tier0.log
```

Переводы строк вместо `;` — падение одного скрипта не остановит следующие.

**Что читать:**

`check_block_cache.py` — строка `16 бит`. Там квантизация тождественна, так
что это **не измерение хранения**, а уровень арифметического шума оконного
прогона, и эталона для него не существует: сравнивать не с чем. В bf16 она не
ноль и не обязана быть нулём. Помечается она только если сдвинулось решение,
которое реально фиксируется (`argmax@k` < 100%) — по последствию, а не по
величине. Порог на саму ошибку тут был бы числом, принесённым из другого
места; один раз так и вышло, проверка сработала впустую. Резкий контроль —
`--dtype float32`.

**Первая строка каждой таблицы — `scram`, пол случайности.** Это 16-битный
кэш, у которого записи перемешаны вдоль оси токенов: распределение в точности
как у идеального, информации ноль. Ни у ошибки, ни у argmax нет осмысленного
нуля без этой строки — два прогона одной модели совпадают во многом просто по
априорным предпочтениям. Строка на уровне пола не несёт ничего, какой бы
маленькой ни выглядела её ошибка, и порядок между такими строками — шум, а не
ранжирование. Скрипт помечает их сам.

**Доля маски метётся по префиксу**, окно остаётся под маской (`--window-mask-ratio`,
по умолчанию 1.0). Это разные вещи: префикс кэшируется, окно декодируется, и
шаг сэмплера смотрит на окно замаскированным. Ранняя версия скрипта мела их
вместе, из-за чего ни одной реалистичной конфигурации в таблице не было.

**Реалистичная строка — `0.00`.** Префикс это закрытые блоки, а закрытый блок
раскрыт полностью. Остальные доли отвечают на следующий вопрос: во что обойдётся
кэширование ещё и текущего, частично замаскированного блока — там устаревание
перестаёт быть структурно нулевым. Высокие доли, скорее всего, вырождены:
кэшированные позиции несут одну и ту же строку эмбеддинга, терять там почти
нечего, и пол это покажет.

**Строка `decision margin`** в шапке каждой таблицы — зазор между первым и
вторым кандидатом на тех позициях, что фиксируются. Это и есть величина, от
которой зависит допустимая разрядность кэша, и она **не константа модели**: чем
выше доля маски, тем ближе решения к ничьей. Строка с относительной ошибкой `e`
двигает логиты примерно на `e × mean|logit|`; когда это дотягивается до зазора,
argmax начинает переворачиваться.

Четыре колонки, по возрастанию строгости:

| колонка | что говорит |
|---|---|
| `rel. err` | сдвиг логитов; ниже порога dtype не значит ничего |
| `argmax` | доля позиций окна с сохранённым argmax — **верхняя граница ущерба** |
| `argmax@k` | то же среди `--commit-k` самых уверенных, то есть тех, что реально фиксируются на шаге |
| `slots@k` | совпали ли вообще сами эти позиции |

Читать надо `argmax@k`. Плоский `argmax` взвешивает все 32 позиции окна
одинаково, а сэмплер — нет: он фиксирует самые уверенные, остальные остаются
под маской и решаются заново на следующем шаге. Перевернувшийся argmax там, где
коммита не было, не стоит ничего. При высокой доле маски позиции почти
вырождены и плоское число проседает само по себе — это не ущерб.

`slots@k` ловит вторую поломку: токены могут быть правильные, а порядок
раскрытия — сдвинутый. `argmax@k` = 100% при `slots@k` < 100% означает именно
это. `n/a` — в окне нет замаскированных позиций (доля маски 0.00), фиксировать
нечего.

`--commit-k` по умолчанию 4. При штатном расписании (`steps == gen_length`)
фиксируется один токен за шаг, так что это первые несколько коммитов блока.

Длина по умолчанию 256 токенов (`--blocks 8`); для сопоставимости с оценкой
на 512 — `--blocks 16`.

`measure_drift.py` — колонка `stale(prefix)` у LLaDA2.0 обязана быть **нулём**
(блочно-каузальная маска), у LLaDA-1.5 — **ненулевой** везде (двунаправленное
внимание, ничего не финально). Это структурное утверждение в числах.

**Ось группировки K (`--key-axes`) важнее всех остальных ручек.** `channel` —
группа вдоль head_dim, `token` — вдоль оси токенов. На `token` четыре бита
неотличимы от точного кэша (94.79% против контрольных 94.79%), на `channel` те
же четыре бита стоят шести-двенадцати пунктов. Два вывода, записанные здесь
раньше как установленные, оказались тенями этой оси и **сняты**: размер группы
на верной оси не значит ничего (94.79% и при 32, и при 128 — брать надо 128,
там накладные 6.25% вместо 25%), и асимметрия K/V схлопывается до 1.05σ.
Подробности и числа — `HANDOFF.md`, раздел 3.

Развёртку K/V и биты × группу мерить **только указав ось явно**: неверная ось
стоит больше любого перераспределения битов, поэтому на ней такая развёртка
меряет ось и называет это асимметрией. Скрипт печатает ось в шапке.

`check_router.py` — **измерено, вопрос закрыт.** 19 роутеров это 9.96M
параметров, 0.061% модели. При 4 битах сохраняется 78% маршрутов, при 8 битах
95%, при 2 битах 28%. То есть четырёхбитный роутер меняет каждый пятый выбор
эксперта — при том, что четырёхбитные веса самих экспертов не дают измеримой
разницы (p = 0.44). Исключение роутера из квантизации заслужено, а не
перестраховка.

Маршруты устойчивее на раскрытом полотне (95.1% против 90.7% при 8 битах) —
тот же механизм, что и у зазора решения: при полной маске оценки экспертов
стоят у ничьей.

### Часы, нужна карта

Оценка на GSM8K. При полотне 512 — **3–10 часов на прогон**, зависит от
соседей. При 256 вчетверо дешевле.

```bash
cd ~/quantization/DLLMQuaRot && CUDA_VISIBLE_DEVICES=N nohup bash -c '
export TF20=$HOME/tf457 PYTHONUNBUFFERED=1
PYTHONPATH=$TF20 python scripts/evaluate.py --model inclusionAI/LLaDA2.0-mini \
  --model-type llada2_moe --n-eval 200 --gen-length 512 --eval-steps 512 \
  --out out/fp16_g512.json' > out/fp16_g512.log 2>&1 &
```

Ключевые флаги:

| флаг | что делает |
|---|---|
| `--quantize` | прогнать конвейер перед оценкой |
| `--rtn` | вместо CGQ — простое округление, без калибровки |
| `--w-bits` / `--a-bits` | биты весов и активаций |
| `--a-group-size 128` | группа для активаций; **решает всё** (26% против 78% на 1.5) |
| `--rotate` | QuaRot |
| `--kv-cache --kv-bits N` | кэш префикса, квантованный |
| `--kv-key-bits` / `--kv-value-bits` | раздельная точность K и V |
| `--kv-masked-bits` | точность для замаскированных позиций |

### Сутки, только осознанно

Квантизация весов. 20.5 часа на занятой карте, около полутора на свободной.
Контрольные точки после каждого блока, при падении продолжает с недоделанного.

```bash
PYTHONPATH=$TF20 python scripts/quantize.py --model inclusionAI/LLaDA2.0-mini \
  --model-type llada2_moe --w-bits 4 --a-bits 4 --a-group-size 128 --rotate \
  --seq-len 256 --gen-length 512 --block-length 32 --steps 128 \
  --checkpoint-dir out/ckpt_w4a4 --save out/llada2mini_w4a4
```

`--gen-length 512` в калибровке — не косметика: со 128 голодало большинство
экспертов, с 512 осталось 2%.

## 4. Работа с сохранённой моделью

`out/llada2mini_w4a4` содержит **квантованные повёрнутые веса** и **не
содержит** квантизаторов активаций: `save_pretrained` пишет тензоры, а у
квантизатора активаций сохраняемого состояния нет.

**Не передавать `--rotate`** — поворот уже вплавлен, второй её уничтожит.

Оценить в режиме W4A4 (веса не трогаем, активации возвращаем):

```bash
--model $PWD/out/llada2mini_w4a4 --quantize --rtn --w-bits 16 --a-bits 4 --a-group-size 128
```

`--w-bits 16` веса не меняет: квантизатор при 16 битах выключен. `--rtn`
навешивает обёртки без запуска солвера — секунды вместо суток.

Путь в `--model` должен быть **абсолютным** или относительным от текущего
каталога; `from_pretrained` принимает и имя на HuggingFace, и путь.

## 5. Диагностика

### Прогон завис или ползёт

```bash
ps -o pid,etime,time,stat -p $(pgrep -f "^python scripts/evaluate.py")
```

`ELAPSED` против `TIME`. Процессорное время около нуля при часах прошедшего —
**заблокирован**. Часы процессорного времени — **считает, просто медленно**.

Заблокирован — почти наверняка файловая блокировка датасета от убитого
прогона:

```bash
find ~/.cache/huggingface -name "*.lock" -mmin +60 -ls | head
find ~/.cache/huggingface -name "*.lock" -delete
```

Считает — смотреть скорость в логе. Прогресс печатается каждые 5 задач и
сообщает `Ns/question, M min left`.

### Где лог

```bash
ls -l /proc/<PID>/fd/1     # куда уходит вывод
ls -l /proc/<PID>/cwd      # откуда запущен
```

### Сколько наших процессов

```bash
pgrep -af "quantize.py|evaluate.py|memory.free|check_"
```

Сторож (`bash -c ... while ...`) и питон — **разные процессы**. Убивать оба.

## 6. Грабли запуска

**Рабочий каталог.** `out/` относителен. Если запускать не из репозитория,
перенаправление вывода падает с `No such file or directory`, а сам прогон
может не найти скрипт. Ставить `cd` **внутрь** `bash -c`, а не только снаружи.

**`cd X && nohup ... & sleep 2 && tail`** уводит в фон весь список вместе с
`cd`, и `tail` выполняется в старом каталоге. Разделять на две команды.

**Буферизация.** При перенаправлении в файл Python копит вывод блоками, и
`tail -f` показывает пустоту. Лечится `PYTHONUNBUFFERED=1`.

**Два сторожа.** Запущенная дважды очередь даёт два ожидающих процесса; оба
сработают и запустят два прогона на одну карту. Хуже: если оба пишут в один
`--checkpoint-dir`, они портят друг другу блоки.

**Переименование карт.** `CUDA_VISIBLE_DEVICES=5` делает пятую карту «GPU 0»,
и все сообщения об ошибках говорят про GPU 0. Это она и есть.

**`--device-map auto`** раскладывает модель по всем видимым картам; тогда
`CUDA_VISIBLE_DEVICES` должен перечислять несколько, а `preflight_memory`
считает сумму. Путь рабочий, но медленный: активации ходят между картами.

**Сторож, ждущий файл**, не отличает «ещё не появился» от «прогон умер и не
появится никогда». Цеплять лучше к завершению PID.

## 7. Известные скорости

| операция | свободная карта | занятая |
|---|---|---|
| слой в солвере CGQ | 0.3 с | 8–17 с |
| полный прогон квантизации | ~1.5 ч | 20.5 ч |
| задача GSM8K, полотно 512 | ~1 мин | 3+ мин |
| загрузка модели с диска | 10–15 с | |

Решатель GPTQ — это тысячи крошечных ядер подряд, он упирается в задержку
запуска и от конкуренции страдает сильнее всего. То же относится к MoE: код
чекпойнта перебирает 256 экспертов циклом на Python, почти пять тысяч мелких
умножений на каждый прогон.

**Почему полотно 512 такое дорогое.** Наш сэмплер прогоняет **всю**
последовательность на каждом шаге, включая ещё не начатые блоки: 512 шагов ×
~700 токенов ≈ 350 тысяч токен-проходов на задачу. Родной сэмплер модели режет
окно по концу текущего блока, наш — унаследован от LLaDA-1.5, где резать
нечего. Кэш это чинит: один полный прогон на блок вместо одного на шаг.

## 8. Что запускать в первую очередь

1. Четыре дешёвых замера на процессоре (раздел 3). По тезису измерений пока
   ноль, и это единственное, что их даёт.
2. Сверка `--kv-cache --kv-bits 16` против обычного пути на 20 задачах. Она же
   первое число про кэш, она же способ ускорить все дальнейшие оценки.
3. База FP16 при 512 и W4A4 сохранённой модели — числа для предпосылки.

Полный список с зависимостями — в `HANDOFF.md`, раздел 10.
