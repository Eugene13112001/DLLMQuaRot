Файл для продолжения в новой сессии. Числа ниже — измеренные на реальных

## 1. Что за проект

Цель исследования: **квантизация KV-кэша для диффузионных LM**. Такого
ещё нет в литературе — это и есть новизна. QuaRot для LLaDA-1.5 / LLaDA2.0 —
поставленная предпосылка, база, на которой замеряется кэш.

Репозиторий: `https://github.com/Eugene13112001/DLLMQuaRot.git`
Сервер: 8×H200, путь `/data/users/evgeniystep/quantization/DLLMQuaRot`.

Реализовано: DLLMQuant (TMAS + IA-AQ + CGQ) и QuaRot (R1/R2/R3), обе как в
своих статьях, адаптированные под диффузию. Квантизация **симулированная**
(fake quant): ускорения и уменьшения файла нет, меряется только качество.

## 2. Измеренные результаты — LLaDA-1.5-8B

GSM8K, реальные веса. Источник: `out/compare.json`, `out/gsm8k_*.json` на сервере.

| Конфигурация | GSM8K | Комментарий |
|---|---|---|
| FP16 | **84.5%** | база |
| W4A16 (только веса, 4 бита) | **83.0%** | в пределах шума ±2.6 |
| W4A4, активации per-token | **26.0%** | развал |
| W4A4, активации group-128 | **78.0%** | рабочий режим |

### Откуда каждая строка — команда и файл

Единого файла со сравнением FP16 ↔ W4A4 **нет**. Это четыре независимых
прогона `evaluate.py`, каждый пишет свой `gsm8k_*.json`. Таблица выше
собрана из них вручную.

| строка | команда | файл |
|---|---|---|
| FP16 | без `--quantize` (по умолчанию `--w-bits 16 --a-bits 16`) | `out/gsm8k_fp16.json` |
| W4A16 | `--quantize --w-bits 4` | `out/gsm8k_w4a16.json` |
| W4A4 per-token | `--quantize --w-bits 4 --a-bits 4` | `out/gsm8k_w4a4.json` |
| W4A4 group-128 | то же + `--a-group-size 128` | `out/gsm8k_g128.json` |

```bash
python scripts/evaluate.py --model GSAI-ML/LLaDA-1.5 --quantize --w-bits 4 --a-bits 4 --a-group-size 128 --n-eval 200 --out out/gsm8k_g128.json
```

Ключевой момент по флагам: `--a-group-size` **не задан** → активации идут
`per_token`, одна шкала на токен. Задан → `per_group`. Это и есть те самые
52 пункта. Гранулярность весов переключается отдельным `--group-size`.

**Перед тем как класть эти числа в текст работы**, открыть блок `config` в
каждом из четырёх файлов и сверить `n_eval`, `gen_length`, `eval_steps`.
Прогоны делались в разное время; блок `config` существует ровно затем, чтобы
это можно было проверить, а не вспоминать. Имена файлов выше — по схеме
именования; на сервере сверить фактические.

Отдельно: `compare.json` — это **не** про W4A4 и не замена этой таблице. Там
9 рецептов при фиксированной разрядности, и меряется в основном fidelity,
а колонка `gsm8k` появляется только при `--gsm8k`.

### Три вывода, на которых всё держится

**(а) 4-битные веса почти бесплатны.** 83.0 против 84.5 — разница внутри
доверительного интервала. Вся сложность в активациях, не в весах.

**(б) Гранулярность активаций решает всё.** 26.0% → 78.0% при одинаковых
прочих настройках, **+52 пункта**, единственное отличие — одна шкала на
токен против одной на группу из 128 каналов. Это самый крупный эффект во
всём проекте.

**(в) Поворот (QuaRot) — вторая по важности вещь.**

| | fidelity | KL |
|---|---|---|
| без поворота | 42.5% | 2.64 |
| с поворотом | 88.9% | 0.132 |

### Отдельно: teacher-forced fidelity ВРЁТ

Две конфигурации из таблицы выше (26% и 78% на GSM8K) различаются по
fidelity всего на **2.3 пункта** (88.9 против 91.2). То есть метрика с
разбросом 2 пункта представляет разрыв в 52 пункта.

Причина: референсные состояния берутся из FP16-траектории, поэтому
квантованная модель никогда не идёт по своему пути. Дрейф уверенности
меняет порядок раскрытия токенов, а раскрытие необратимо.

**Следствие для новой сессии: не доверять fidelity как основной метрике.**
Для этого написан `dllmquant/eval/trajectory.py` — модель идёт своим путём
(`capture_reference` / `measure_divergence`), отдаёт `exact_match`,
`final_agreement`, `first_divergence_step`, `divergence_mask_ratio`.

### Выбросы в каналах зависят от доли маски

Crest factor (max|x| / rms(x)) активаций:

| доля маски | crest |
|---|---|
| 1.0 (всё замаскировано) | 39.1 |
| 0.0 (всё раскрыто) | 6.9 |

Гипотеза (**не проверена**): это профиль самой строки эмбеддинга `[MASK]`.
Проверить можно, посмотрев на строку `embed_tokens.weight[mask_id]`.
Практическое следствие: ранние шаги траектории квантовать труднее, чем
поздние — там же, где кэш обновлять надо чаще.

Время полного прогона квантизации: **~100 минут** (не 35, как я оценил
сначала — оценка была снята с момента, когда GPU был свободен).

## 3. Какие файлы что содержат

Общее правило: **рядом с каждым `.json` пишется `.csv` с тем же именем.**
JSON — полная запись, CSV — та же таблица, которую можно открыть и
отсортировать. CSV производный, восстанавливается из JSON.

### `report.json` — от `scripts/quantize.py --report`

Что происходило во время квантизации. Ключи:

| ключ | что внутри |
|---|---|
| `layers` | список слоёв: `name`, `block`, `proxy_loss`, `tokens`, `weighted`, `seconds` |
| `ia_aq` | подобранные шкалы активаций (что нашёл MSE-поиск) |
| `n_calibration` | сколько калибровочных снимков реально собрано |
| `unweighted_layers` | **важное** — слои, упавшие на равномерные веса вместо certainty-взвешивания, потому что число токенов не совпало. Для MoE тут будут все экспертные проекции |
| `seconds` | время |

`proxy_loss` — ошибка восстановления выхода слоя. Чем ниже, тем лучше.
Сопутствующий `report.csv` — это та таблица, которую сортируют, когда ищут
слой, которому досталось больше всех.

### `gsm8k_*.json` — от `scripts/evaluate.py --out`

| ключ | что внутри |
|---|---|
| `config` | полный набор настроек прогона: `model`, `w_bits`, `a_bits`, `group_size` (веса), `a_group_size` (активации), `rotation`, `ia_aq`, `certainty_weighting`, `rtn`, `gen_length`, `eval_steps`, `n_eval` |
| `accuracy`, `correct`, `total` | результат |
| `cut_off`, `cut_off_wrong` | сколько ответов обрезано по длине генерации, и сколько из них из-за этого неверны. Отделяет «модель не умеет» от «не хватило бюджета» |
| `samples` | **все** завершения: `question`, `pred`, `gold`, `correct` |

Два момента, ради которых это так устроено:

- `samples` хранит каждое завершение, а не выборку. Генерация стоит часов,
  и изменение парсера ответа не должно требовать перегенерации.
  `scripts/rescore.py out/gsm8k_*.json` переразбирает их на месте.
- `config` содержит **и** `group_size`, **и** `a_group_size`. Раньше веса
  своей записи не имели, и у готового файла нельзя было спросить, какая
  гранулярность у весов — а это ровно тот вопрос, который решает, лежат ли
  два результата на одной оси. `gen_length` там по той же причине.

### `compare.json` — от `scripts/compare.py --out`

Список из 9 записей, по одной на рецепт: FP16, RTN, DLLMQuant (full), три
абляции (−TMAS / −IA-AQ / −CGQ-веса), QuaRot на текстовой калибровке,
QuaRot на траекторной, DLLMQuant + QuaRot.

В каждой записи: `name`, `kind`, `fidelity` (`top1`, `kl`, `conf_delta`,
`per_bucket` — разбивка по доле маски), `seconds`; у `dllm` ещё
`mean_proxy_loss` и `layers`; `gsm8k` появляется только при `--gsm8k`.

**Осторожно с этим файлом:** `fidelity` здесь — teacher-forced, а она врёт
(см. §2). Строки, различающиеся по ней на 2 пункта, различались на 52
пункта GSM8K. Абляции по ней ранжировать нельзя.

### `*_top.json` + 2 CSV — от `scripts/inspect_activations.py`

Откуда взялись crest-факторы из §2. Четыре файла с общим префиксом:

- `_top.json` — топовые каналы-выбросы, сгруппированные по доле маски → слою.
  Здесь видно, **те же ли это каналы** на разных долях маски.
- `_layers.csv` — строка на (доля маски, слой): `crest`, `kurtosis`,
  `max_abs`, `median_channel_abs`, `outlier_ratio`, `worst_token`.
- `_channels.csv` — то же в развёрнутом виде, строка на канал с рангом.
- `_summary.txt` — текстовая сводка.

### Чекпоинты — `checkpoint_dir`, не JSON

- `meta.json` — отпечаток конфига. При несовпадении загрузка **отказывает**,
  а не подмешивает блоки от другого прогона.
- `snapshots.pt` — калибровочные снимки TMAS.
- `block_0000.pt`, `block_0001.pt`, … — по файлу на блок.

Прогон на ~100 минут можно продолжить с места обрыва.

## 4. Где сейчас затык

**LLaDA2.0-mini не загружается.** Причина — версия transformers.

Окна версий у двух моделей **не пересекаются**:

| модель | transformers | почему |
|---|---|---|
| LLaDA-1.5 | 4.38 – 4.46 | выше ломается `tie_weights()` и остальное |
| LLaDA2.0 | **4.56+** | нужны `dynamic_rope_update`, `TransformersKwargs` |

Одним venv обе модели не обслужить. Нужен **отдельный venv для LLaDA2.0**.

Проверено скачиванием и вскрытием колёс — оба символа присутствуют в:

```
4.56.2  dynamic_rope_update: True | TransformersKwargs: True
4.57.1  dynamic_rope_update: True | TransformersKwargs: True
5.0.0   dynamic_rope_update: True | TransformersKwargs: True
```

Рекомендация: **4.57.1** — самый свежий 4.x, путь `dtype=` (переименование
`torch_dtype` → `dtype` произошло в 4.56, в `_dtype_kwargs` это учтено).

**pypi с сервера недоступен** — ставили офлайн-бандлом колёс. Бандл для
4.51.3 уже собирался (32 МБ, 18 колёс, tokenizers 0.21.4); для 4.57.1 надо
собрать такой же.

**Второе, отдельно:** в последнем неудачном прогоне `CUDA_VISIBLE_DEVICES`

`GPU 0: NVIDIA H200, 2.2 GB free`. Сервер общий. LLaDA2.0-mini нужно ~36 ГБ.

## 7. Устройство кэша (то, что уже написано)

`dllmquant/cache.py`:

- `KVCacheConfig`: `decoded_bits` / `masked_bits` — раскрытые и
  замаскированные позиции можно держать в разной точности, потому что K/V
  замаскированной позиции всё равно перезапишется, когда токен раскроется,
  а у раскрытой — окончательный.
- `group_size=128`, `clip_ratio=0.95`.
- Политики обновления: `never` / `every_n` / `block` / `mask_ratio`.
  `mask_ratio` — адаптивная: всё замаскировано → обновлять каждый шаг,
  всё раскрыто → редко (`min_interval`..`max_interval`).
- Граница блока форсирует обновление при любой политике.
- `measure_drift` **разделяет два источника ошибки**: `staleness`
  (кэш устарел) и `quantization` (округление). Без этого интервал
  обновления не к чему подгонять.

## 8. Грабли, на которые не наступать второй раз

- `.gitignore`: `models/` матчится на любой глубине и молча выкидывал
  `dllmquant/models/` из репозитория. Сейчас якорь `/models/`.
- Матрицы Пэли **не симметричны** — в `fast_hadamard` нужен `H_m @ y`, а не
  `y @ H_m`. На степенях двойки не видно, ломается на 96 и 12288.
- `ff_out` — это и down-projection блока, и LM head; `gate` — подстрока
  `gate_proj`. Отсюда раздельные `skip_leaf_names` (точное имя листа) и
  `skip_patterns` (подстрока).
- Fake-квантайзеры повышали dtype (fp32-шкала × bf16-активация) и роняли
  SDPA на «Expected query, key, and value to have the same dtype». Лечится
  `.to(x.dtype)` на выходе квантайзера.
- Численный допуск инвариантности в bf16 бесполезен: 1–3.7% — это уровень
  шума (в fp32 — 2e-7). Поэтому в `rotation_plan` структурная проверка
  покрытия, а не численная.
- `OnlineHadamard` переименовывал `ff_out` → `inner` и тем самым выкидывал
  слой из групп CGQ. Обёртка обязана сохранять исходное имя атрибута.
- Зонд внимания пропускал `attn_norm` перед `att_proj` (сеть pre-norm).
- Извлечение ответа GSM8K по «последнему числу» ошибалось на «7 dozens ...
  in 4 weeks» → приоритет маркеров (`\boxed{}` → «answer is N» → жирный →
  последнее число) плюс контракт в промпте.
- `hash()` для строк в Python солится на процесс — тестовый токенизатор был
  недетерминированным. Заменено на FNV-1a.

## 9. Открытый вопрос по методу

Пользователь заметил (и был прав), что выбрасывать внимание от раскрытых
токенов нельзя: выход раскрытого запроса отбрасывается только на последнем
слое, а внутри сети он влияет на всё. Поэтому вместо жёсткого исключения
стоит `decoded_query_weight = 0.5` — зеркально коэффициенту в CGQ
(`c_j = 0.5` для раскрытых, `0.5 + conf_j` для замаскированных).
Значение 0.5 взято по аналогии, **не подобрано экспериментально**.
