### Формулировки для статьи

1. Не «KIVI», а **«квантование KIVI без окна»** (без остатка в полной точности), всегда с честными битами: 2 бита кода ≈ 3 честных бита. Где есть окно, писать его длину (32 или 128) и честные биты с учётом окна.
2. Блок 4 — **отдельные веса модели**: у SDAR под каждый размер блока обучена своя модель. Писать «у модели SDAR с блоком 4», без обобщения «маленький блок устойчивее к сжатию». Учитывать, что эта модель и без сжатия пишет меньше токенов за шаг (2,3 против 3,2 у блока 32).
3. Ненадёжность уверенности сжатой модели — **гипотеза**, пока её не проверит теневая модель (этап 2). Опора сейчас — 396 задач с разницей −0,8 против −2,8, это в пределах шума.
4. Расхождение с SoloQ описывать честно: их цифру (59,29) не повторили; в рамках наших проверок обвал такого размера даёт только общая шкала на батч из 32 примеров (66,8), их код недоступен. Не утверждать, что SoloQ ошибся.

## 1.2. Модуль сжатия и самопроверки

Модуль `blockkv/kvquant.py`, KIVI-подобная фейк-квантизация: динамическая, асимметричная min-max, округление до ближайшего.

- Ключи по каналам, значения по токенам, группа 32, минимум и шаг на пример, голову и группу.
- Вариант A: готовые блоки ждут в 16 битах, пока не наберётся группа из 32 токенов, затем группа сжимается один раз.
- Текущий блок не сжимается.
- Честные биты: `биты + 32 / группа`, то есть 2 бита дают 3.
- Режимы: `--kv-bits {2,3,4,8,16}` (16 — модуль работает, но ничего не округляет), `--kv-only {k,v}`, `--key-mode {channel,token}`, `--kv-window`, `--kv-sink`.

Самопроверки на 20 задачах, порог 0,9, группа 32:

### Выводы по 1.3

1. Цифра SoloQ 59,29 не воспроизведена ни в одном варианте. Ближайший вариант, общая шкала на батч: 66,8, разница 7,5 пункта при допуске ±3.
2. Модуль выглядит верным: официальная формула, независимый аудит, 4 бита почти без потерь. Но это не доказывает, что наша цифра верна, а их нет. Цифры BitSieve получены при чтении только 64 записей на голову и опровержением не служат.
3. Разница между шкалой на пример и шкалой на батч (−4,3 против −20,1 при тех же 2 битах) показывает, что детали реализации меняют вред в разы.
4. Утверждать в статье, что SoloQ ошибся, нельзя. Можно написать, что цифру не воспроизвели, и показать проверки.

### Цифры других авторов (поиск 2026-11-08)

Другой опубликованной цифры KIVI в 2 бита именно на Fast-dLLM v2 и GSM8K, кроме SoloQ, не найдено. Прочитаны PDF BitSieve и QuMix.

**BitSieve** — не сверка для нашего опыта. Цифры 76 и 78 получены при другом режиме: Fast-dLLM-v2-7B, порог 0,95, 200 задач, один прогон, модель читает только 64 выбранные записи на голову, первые два слоя плотные, сжатие действует и на выбор, и на внимание. При чтении 64 записей шум усредняется по гораздо меньшему числу токенов, поэтому вред может быть больше, чем при чтении всего кэша. Округление у них по той же формуле, что у KIVI: ключи по каналам с группой из B токенов (при B=32 это наша группа), значения по токенам группами по 32 канала, 1 бит на минимум и шаг. Отличие в выборе записей. При 2 битах: только ключи 76,0, только значения 78,0, оба 74,0 (−10,5). При 4 битах потерь почти нет: 84,0 против 84,5.

3. **Одна кривая по ошибке кэша.** Ошибка квантователя меряется только на сжатых токенах, поэтому с окном она та же, что без окна (0,026 / 0,169 при w128), хотя сжата лишь часть памяти. Для общей кривой нужна ошибка по всему кэшу: ошибка × доля сжатых токенов (`tax_table` теперь печатает её в столбце «По всему кэшу», нужен повторный запуск). Грубо для блока 32 по ключам: 4 бита 0,0009 → +1,2%; 3 бита 0,0043 → +1,5%; окно 128 ≈ 0,026 × 0,4 ≈ 0,010 → +5,6%; 2 бита 0,0235 → +17,1%; шум 0,0248 → +19,7% — монотонно. Налог растёт с ошибкой кэша и резко ускоряется между ~0,01 и ~0,02 по ключам.
4. На RULER 4K ответы короткие (медиана 5–9 шагов), поэтому проценты шагов грубые, а зацикливаний нет. Потеря параллельности та же картина: −0,23 токена у блока 4, −0,96 у блока 64.

### Время шага при реальном сжатии — не мерили

Все прогоны используют имитацию квантования (значения округляются и хранятся снова в 16 битах), поэтому памяти и времени они не экономят, и налог измерен только в шагах. На обоих бенчмарках сравниваем KV2 с четырьмя вариантами: `k4v2` (ключи 4 бита, значения 2), `kv2_kb0.0625x8` (6,25% каналов ключей с наибольшим диапазоном в 8 битах), `kv2_rotv` (Hadamard для значений) и `kv2_ktoken_rot` (Hadamard для K и V, ключи квантуются по токенам). Последний вариант меняет и вращение, и ось квантования ключей. Это локальные варианты fake quant по мотивам исследованных методов. Сравнение включает токены за шаг, дополнительные шаги на ответ, метрику качества, повторы, долю ответов у лимита и эффективную разрядность кэша.

Файлы вариантов: `out/longbench/16384/sdar8b_b32_<вариант>.jsonl` и `out/longproc/2k/sdar8b_b32_<вариант>.jsonl`, рядом соответствующие `.log` и `.meta.json`. Для LongProc сохраняем исходный отбор пяти наборов 2K, 20 задач на набор до фильтра длины, seed 0. Числа для вариантов ожидают запуска и проверки.

Контроль по литературе: [TurboQuant, ICLR 2026](https://openreview.net/forum?id=tO3ASKZlok) использует случайное вращение и распределённый по уровням скалярный квантователь. Локальные режимы `kv2_rotv` и `kv2_ktoken_rot` проверяют вращение Адамара с min-max округлением. Для сопоставления с работой нужен отдельный прогон алгоритма TurboQuant в том же раннере. Уже измеренная политика LMDeploy `q42` имеет отдельные результаты выше и квантует также текущий блок. [DECAL](https://openreview.net/forum?id=xQ57THZa4v) исследует налог параллельности при W4A4 и калибрует уверенность фиксации. Результаты переноса этой калибровки на KV2 SDAR приведены в разделах про DECAL выше.

**Дополнение к обзору, 21 ноября 2026.** [QWaF](https://iris.skku.edu/publication/c111_neurips_diffulm_workshop_2026/) — смешанная точность KV, учитывающая направления запросов. Авторы сообщают 97% от оценки FP16 на LongBench с SDAR-8B при 2,22 эффективного бита. По доступной аннотации не удалось подтвердить токены за шаг, порог или зависимость от размера блока. [Программа DiffuLM @ NeurIPS 2026](https://7amin.github.io/diffulm-neurips2026/papers.html) подтверждает устный доклад QWaF и постер BitSieve. [Polestar-Cache](https://openreview.net/pdf/d00aa31fdff2213f651eb03fda946a63cec8ae21.pdf) связывает ошибку приближённого повторного использования KV с падением уверенности, числа токенов за проход и ростом шагов. Источник ошибки у них — дрейф представлений, у нас — округление KV завершённых блоков. [DUET](https://arxiv.org/abs/2611.09239) проверяет разреженное внимание и вычисления текущего блока на SDAR-8B-b32 при 32K; это отдельный класс оптимизации.

### Выбранные методы для следующего эксперимента

- **QWaF** — основной контроль квантования. На SDAR-8B-b32 с порогом 0,9 сравнить с FP16 и KIVI KV2 на прежних ID `qmsum` и `gov_report`, затем повторить на LongProc 2K. Указать эффективные биты, качество, токены за шаг, добавленные шаги, повторы и достижение лимита. Найден локальный полный текст `60_QWaF_Ultra_Low_Bit_KV_Cache.pdf`, публичный код пока не найден. [Карточка QWaF](https://openreview.net/forum?id=EALAEHQG9D)

  **Настройки из локального PDF.** Таблицы 4–5: у SDAR блок 4, четыре шага с фиксированной политикой раскрытия, вход до 4096, по 150 примеров, есть `qmsum`, `gov_report` отсутствует. В таблице 10 ROUGE-L `qmsum` составляет 22,6 / 22,0 / 22,3 для FP16 / KIVI KV2 / QWaF соответственно, при 16 / 2,94 / 1,99 эффективного бита. Это цифры локальной версии PDF, средний результат из публичной аннотации выше относится к другому бюджету. Наш блок 32 с адаптивным порогом 0,9 и входом до 16K проверяет другой режим.

  **Что нужно для запуска.** Использовать только авторскую реализацию. PDF QWaF сообщает о планах выпустить код. PDF [QuMix, заявка ICLR 2027 №46483](https://openreview.net/forum?id=lNkc5LGSt4) указывает, что реализация, калибровка и скрипты оценки входят в отдельные дополнительные материалы. Локальные PDF не содержат встроенных архивов. Для запуска нужен авторский архив и проверка того, какой версии метода он соответствует. Калибровочный протокол из QWaF: 64 окна WikiText по 512 токенов, моменты Q/K до RoPE, группы K по 32 токена, V по токенам в 2 бита. Текущий блок и неполная группа остаются в исходной точности.

  **Выходы.** `out/qumix/sdar8b_b32_t0.9/{longbench,longproc}/sdar8b_b32_{base,kivis2r128,qmxmatchkivi2ts}.jsonl` с соседними `.meta.json`. Все три режима прогоняются заново с одним декодером, промптами и BF16 весами. `kivis2r128` — авторский KV2 с остатком 128, `qmxmatchkivi2ts` — QuMix при бюджете указанного в статье KV2. JSONL включает оценки, тексты, шаги, токены и оценку эффективных битов по фактически квантованным позициям. Сверять измеренную разрядность по каждому набору: соответствие бюджетов в статье задано при 4K, а длинные входы меняют долю точного остатка.
- **Polestar-Cache** — контроль влияния ошибки кэша на параллельность. Авторский Polestar поддерживает LLaDA и Dream, в опубликованном списке моделей SDAR отсутствует. Сначала воспроизвести обычный режим и режим обновления кэша на поддерживаемой модели. Прямой перенос на SDAR требует отдельного обоснования и адаптации: завершённый префикс SDAR стабилен, поэтому его пересчёт с тем же квантованием не исправляет округление. При анализе Polestar отделять эффект обновления кэша от изменения правила фиксации. [Код авторов](https://github.com/gt-synergy-lab/Polestar)

**Получен авторский архив QuMix** `46483_QuMix_Query_Guided_Mixed_Supplementary Material.zip`. Локально распакован в `out/qumix_author/qumix_supplementary/` без изменений авторских файлов. `python tests/test_reference.py` завершился с `ALL CHECKS PASSED` на CPU и подтвердил 1,99 / 1,69 / 1,55 эффективного бита у трёх поставляемых конфигураций SDAR. Архив содержит калибровку `calib/sdar_calib_paper.pt`, авторский раннер `accuracy/sdar/qumix_eval.py` и генератор `accuracy/sdar/generate.py`. Раннер принимает `qmsum` и `gov_report`, `--block 32 --steps 32 --remask low_confidence_dynamic` используют заданный в коде порог 0,9. Публикационная калибровка относится к базовому SDAR с блоком 4. Для `SDAR-8B-Chat-b32` следует пересобрать её авторским кодом. Существующий JSON `--dump` сохраняет оценку, текст, токены и длину входа, а счётчик шагов и поддержка LongProc требуют отдельной обвязки. GPU-прогонов пока нет.

Для запуска используется `GPU=1 bash scripts/qumix_sdar.sh`. Скрипт загружает SDAR-8B-b32 в отдельный каталог, выполняет калибровку из авторских скриптов и запускает сначала LongBench, затем LongProc. Индекс карты указывать по наличию ресурсов. `LONGBENCH_DATA` и `LONGPROC` переопределяют исходные пути. Скрипт требует окружение с зависимостями QuMix из `third_party/qumix/requirements/sdar.txt` и зависимостями собственных оценщиков LongBench и LongProc. Модуль `blockkv.run_qumix` загружает авторские кэш-хуки без авторского цикла оценки и использует проектный жадный декодер SDAR с адаптивным порогом 0,9. Так top-k=1 из авторского режима не сводит уверенность к единице. Сторонние файлы скопированы из архива SHA-256 `4c8354776598999645cdc48563adb142fe01ee37787831bc52e53bab36d01244`.

До загрузки модели проверяются файлы датасетов, доступ к CUDA и пакеты `rouge` / `rouge-score` для LongBench. Во время записи KV раннер оставляет логиты только последней позиции, поскольку декодер не использует их на этих проходах. На шагах денойзинга остаются логиты всех позиций для вычисления уверенности.

Повторный LongBench на `qmsum` и `gov_report` охватывает блоки 4, 8, 16 и 32, по 100 задач на набор. Для каждого блока `B` отдельная калибровка и каталог `out/qumix/sdar8b_b<B>_t0.9/`. Остальные режимы — `longbench/sdar8b_b<B>_base.jsonl` и `longbench/sdar8b_b<B>_qmxmatchkivi2ts.jsonl`. Авторская аллокация QuMix рассчитана под 2,94 эффективного бита при 4K. | `out/probe/` | теневой разбор шага `blockkv.kv_probe`: `lp_sdar8b_b<блок>.json` / `.log` — LongProc, SDAR, схемы 2 / 3 / 2k / 2v, ответ до 1024, замеры в начале ответа; `lp3_sdar8b_b<блок>` — ответ до 9216, замер на каждом 16-м шаге до 64 на задачу, плюс `commit_*` и разбивки `bins` (conf / pos / fill); в `.json` по схеме ошибки кэша, `conf_drop`, `gap_shrink`, `flip`, `fall_below`, `kl`, `attn_block_exact`, `attn_block_quant` | теневой разбор шага |
| `~/third_party/BitSieve/results/check/<задача>/` | их код на GSM8K или qmsum (`BENCH=qmsum`) | сверка с кодом BitSieve |

Аудит кэша (`blockkv.audit_cache`) пишет только в терминал, файла нет. Несжатые прогоны с порогами 0,8 и 0,85 для кривой «точность против шагов» лежат в `out/stage1/full/` (`sdar8b_b32_t0.8`, `sdar8b_b32_t0.85`), по 1319 задач. Повторы главных прогонов — с окончанием `_rep`: `out/stage1/full/sdar8b_b32_t0.9_rep`, `out/stage1_kv/full/sdar8b_b32_t0.9_kv2_rep`, `..._kv2_T0.8_rep`.

### Как читать имя

`<модель>_b<блок>[_t<порог>][_kv<биты>[k|v]][_g<группа>][_w<окно>][_s<sink>][_k<способ>][_T<температура>][_rep]`

| Часть | Значение | По умолчанию |
|---|---|---|
| `sdar8b`, `fastdllm` | модель: SDAR-8B или Fast-dLLM v2 | |
| `b32` | размер блока | |
| `t0.9` | порог уверенности; без `_t` в `out/stage1/` — порог 1,0 | |
| `kv2`, `kv4` | биты кэша (KIVI: ключи по каналам, значения по токенам) | без `kv` — без сжатия |
| `kv2k`, `kv2v` | сжаты только ключи / только значения | |
| `kvk4v2`, `kvk2v4` | ключи и значения со своими битами (k4v2: ключи 4, значения 2) | |
| `_ktoken_rot` | схема с поворотом Адамара (QuaRot-подобная), ключи по токенам | |
| `_pc<N>` | вход подан в кэш кусками по N токенов (проверка; 0 — одним проходом) | |
| `_g64` | размер группы | 32 |
| `_w32` | последние 32 токена не сжаты | 0 |
| `_s4` | первые токены (sink) не сжаты | 0 |
| `_ktoken` | ключи по токенам вместо каналов | по каналам |
| `_T0.8` | температура фиксации DECAL | 1,0 |
| `_kivi` | округление официальным кодом KIVI (`quant/new_pack.py`, `--kv-impl kivi`) вместо нашего | наш код |
| `_rms` | `--torch-rmsnorm`: RMSNorm SDAR в PyTorch вместо Triton-ядра с автоподбором; прогон воспроизводим между картами (`TORCH_RMSNORM=1` в скриптах) | Triton-ядро |
| `_noise` | контроль: вместо округления равномерный шум ±половина шага той же группы (`--kv-impl noise`), ошибка той же величины; биты в имени задают шаг | округление |
| `_T0.8` в `out/stage1/` | несжатая модель с температурой фиксации (контроль для DECAL) | 1,0 |
| `_n512` | ответ ограничен 512 токенами | 4096 SDAR, 2048 Fast-dLLM |
| `_rep` | повтор того же запуска (проверка воспроизводимости) | |

Пример: `out/stage1_kv/full/sdar8b_b32_t0.9_kv2_w32_T0.8.jsonl` — SDAR-8B, блок 32, порог 0,9, кэш 2 бита, 32 последних токена не сжаты, температура 0,8, все 1319 задач.

## Как воспроизвести

Сводка и сравнение:

```bash
python -m blockkv.summarize out/stage1/full/*.jsonl
python -m blockkv.summarize --compare out/stage1/full/fastdllm_b32.jsonl out/stage1_kv/full/fastdllm_b32_t1.0_kv2.jsonl
```

Прогоны этапа 1.3:

```bash
SUBSET= GSM8K=~/data/gsm8k_test.jsonl HF_HUB_OFFLINE=1 RUNS="fastdllm:32:1.0:2 fastdllm:32:1.0:4 fastdllm:32:1.0:2k fastdllm:32:1.0:2v" GPUS="0 0 1 3" nohup bash scripts/stage1_kv.sh > out/stage1_3.log 2>&1 &
```

Батчевый запуск (нужен `generation_functions.py` из репозитория NVlabs):

```bash
HF_HUB_OFFLINE=1 python -m blockkv.fastdllm_batch --gen-fn ~/data/generation_functions.py --data ~/data/gsm8k_test.jsonl --out out/batch/kv2_shared.jsonl --kv-bits 2 --shared-scale
```

Аудит кэша:

```bash
HF_HUB_OFFLINE=1 python -m blockkv.audit_cache --data ~/data/gsm8k_test.jsonl --limit 20
```
