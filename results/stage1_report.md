### Формулировки для статьи

1. Не «KIVI», а **«квантование KIVI без окна»** (без остатка в полной точности), всегда с честными битами: 2 бита кода ≈ 3 честных бита. Где есть окно, писать его длину (32 или 128) и честные биты с учётом окна.
2. Блок 4 — **отдельные веса модели**: у SDAR под каждый размер блока обучена своя модель. Писать «у модели SDAR с блоком 4», без обобщения «маленький блок устойчивее к сжатию». Учитывать, что эта модель и без сжатия пишет меньше токенов за шаг (2,3 против 3,2 у блока 32).
3. Ненадёжность уверенности сжатой модели — **гипотеза**, пока её не проверит теневая модель (этап 2). Опора сейчас — 396 задач с разницей −0,8 против −2,8, это в пределах шума.
4. Расхождение с SoloQ описывать честно: их цифру (59,29) не повторили; в рамках наших проверок обвал такого размера даёт только общая шкала на батч из 32 примеров (66,8), их код недоступен. Не утверждать, что SoloQ ошибся.

## 1.2. Модуль сжатия и самопроверки

Модуль `blockkv/kvquant.py`, KIVI-подобная фейк-квантизация: динамическая, асимметричная min-max, округление до ближайшего.

- Ключи по каналам, значения по токенам, группа 32, минимум и шаг на пример, голову и группу.
- Вариант A: готовые блоки ждут в 16 битах, пока не наберётся группа из 32 токенов, затем группа сжимается один раз.
- Текущий блок не сжимается.
- Честные биты: `биты + 32 / группа`, то есть 2 бита дают 3.
- Режимы: `--kv-bits {2,3,4,8,16}` (16 — модуль работает, но ничего не округляет), `--kv-only {k,v}`, `--key-mode {channel,token}`, `--kv-window`, `--kv-sink`.

Самопроверки на 20 задачах, порог 0,9, группа 32:

### Выводы по 1.3

1. Цифра SoloQ 59,29 не воспроизведена ни в одном варианте. Ближайший вариант, общая шкала на батч: 66,8, разница 7,5 пункта при допуске ±3.
2. Модуль выглядит верным: официальная формула, независимый аудит, 4 бита почти без потерь. Но это не доказывает, что наша цифра верна, а их нет. Цифры BitSieve получены при чтении только 64 записей на голову и опровержением не служат.
3. Разница между шкалой на пример и шкалой на батч (−4,3 против −20,1 при тех же 2 битах) показывает, что детали реализации меняют вред в разы.
4. Утверждать в статье, что SoloQ ошибся, нельзя. Можно написать, что цифру не воспроизвели, и показать проверки.

### Цифры других авторов (поиск 2026-11-08)

Другой опубликованной цифры KIVI в 2 бита именно на Fast-dLLM v2 и GSM8K, кроме SoloQ, не найдено. Прочитаны PDF BitSieve и QuMix.

**BitSieve** — не сверка для нашего опыта. Цифры 76 и 78 получены при другом режиме: Fast-dLLM-v2-7B, порог 0,95, 200 задач, один прогон, модель читает только 64 выбранные записи на голову, первые два слоя плотные, сжатие действует и на выбор, и на внимание. При чтении 64 записей шум усредняется по гораздо меньшему числу токенов, поэтому вред может быть больше, чем при чтении всего кэша. Округление у них по той же формуле, что у KIVI: ключи по каналам с группой из B токенов (при B=32 это наша группа), значения по токенам группами по 32 канала, 1 бит на минимум и шаг. Отличие в выборе записей. При 2 битах: только ключи 76,0, только значения 78,0, оба 74,0 (−10,5). При 4 битах потерь почти нет: 84,0 против 84,5.

2. **Зацикливания налог не создают.** На них приходится 0–14% лишних шагов там, где налог заметен (2 бита, блоки 8–64, шум, окна у блоков 8 и 64). Большие и отрицательные доли — там, где налог мал или число зацикливаний при сжатии падает (блок 4: 12 → 8, 6, 9), и смысла не имеют. Среднее без зацикливаний — честная мера налога.
3. **Одна кривая по ошибке кэша.** Ошибка квантователя меряется только на сжатых токенах, поэтому с окном она та же, что без окна (0,026 / 0,169 при w128), хотя сжата лишь часть памяти. Для общей кривой нужна ошибка по всему кэшу: ошибка × доля сжатых токенов (`tax_table` теперь печатает её в столбце «По всему кэшу», нужен повторный запуск). Грубо для блока 32 по ключам: 4 бита 0,0009 → +1,2%; 3 бита 0,0043 → +1,5%; окно 128 ≈ 0,026 × 0,4 ≈ 0,010 → +5,6%; 2 бита 0,0235 → +17,1%; шум 0,0248 → +19,7% — монотонно. Налог растёт с ошибкой кэша и резко ускоряется между ~0,01 и ~0,02 по ключам.
4. На RULER 4K ответы короткие (медиана 5–9 шагов), поэтому проценты шагов грубые, а зацикливаний нет. Потеря параллельности та же картина: −0,23 токена у блока 4, −0,96 у блока 64.

### Время шага при реальном сжатии — не мерили

Все прогоны используют имитацию квантования (значения округляются и хранятся снова в 16 битах), поэтому памяти и времени они не экономят, и налог измерен только в шагах. Замер времени шага на настоящих 2-битных ядрах (BitSieve, Fast-dLLM v2: `performance` с фиксированным числом шагов, длины 1–28 тыс. токенов, батчи 1–16) не запускался: нужен код BitSieve на сервере. Перенесён в этап 2 как главный пункт.

## Карта файлов прогонов

Все прогоны лежат на сервере в `~/quantization/DLLMQuaRot/out/` (папка исключена из git; архив после этапа: `tar czf ~/stage1_out_<дата>.tgz out/`). На каждый прогон три файла:

- `.jsonl` — строка на задачу: `idx`, `correct` (для RULER ещё `score` и `task`), `gen_tokens`, `steps`, `nfe`, `forced`, `blocks`, `per_step`, `sec`, `text`; у сжатых — статистика сжатия (честные биты, ошибки ключей и значений). Все цифры отчёта считаются из этих файлов.

### Как читать имя

`<модель>_b<блок>[_t<порог>][_kv<биты>[k|v]][_g<группа>][_w<окно>][_s<sink>][_k<способ>][_T<температура>][_rep]`

| Часть | Значение | По умолчанию |
|---|---|---|
| `sdar8b`, `fastdllm` | модель: SDAR-8B или Fast-dLLM v2 | |
| `b32` | размер блока | |
| `t0.9` | порог уверенности; без `_t` в `out/stage1/` — порог 1,0 | |
| `kv2`, `kv4` | биты кэша (KIVI: ключи по каналам, значения по токенам) | без `kv` — без сжатия |
| `kv2k`, `kv2v` | сжаты только ключи / только значения | |
| `_g64` | размер группы | 32 |
| `_w32` | последние 32 токена не сжаты | 0 |
| `_s4` | первые токены (sink) не сжаты | 0 |
| `_ktoken` | ключи по токенам вместо каналов | по каналам |
| `_T0.8` | температура фиксации DECAL | 1,0 |
| `_kivi` | округление официальным кодом KIVI (`quant/new_pack.py`, `--kv-impl kivi`) вместо нашего | наш код |
| `_rms` | `--torch-rmsnorm`: RMSNorm SDAR в PyTorch вместо Triton-ядра с автоподбором; прогон воспроизводим между картами (`TORCH_RMSNORM=1` в скриптах) | Triton-ядро |
| `_noise` | контроль: вместо округления равномерный шум ±половина шага той же группы (`--kv-impl noise`), ошибка той же величины; биты в имени задают шаг | округление |
| `_T0.8` в `out/stage1/` | несжатая модель с температурой фиксации (контроль для DECAL) | 1,0 |
| `_n512` | ответ ограничен 512 токенами | 4096 SDAR, 2048 Fast-dLLM |
| `_rep` | повтор того же запуска (проверка воспроизводимости) | |

Пример: `out/stage1_kv/full/sdar8b_b32_t0.9_kv2_w32_T0.8.jsonl` — SDAR-8B, блок 32, порог 0,9, кэш 2 бита, 32 последних токена не сжаты, температура 0,8, все 1319 задач.

## Как воспроизвести

Сводка и сравнение:

```bash
python -m blockkv.summarize out/stage1/full/*.jsonl
python -m blockkv.summarize --compare out/stage1/full/fastdllm_b32.jsonl out/stage1_kv/full/fastdllm_b32_t1.0_kv2.jsonl
```

Прогоны этапа 1.3:

```bash
SUBSET= GSM8K=~/data/gsm8k_test.jsonl HF_HUB_OFFLINE=1 RUNS="fastdllm:32:1.0:2 fastdllm:32:1.0:4 fastdllm:32:1.0:2k fastdllm:32:1.0:2v" GPUS="0 0 1 3" nohup bash scripts/stage1_kv.sh > out/stage1_3.log 2>&1 &
```

Батчевый запуск (нужен `generation_functions.py` из репозитория NVlabs):

```bash
HF_HUB_OFFLINE=1 python -m blockkv.fastdllm_batch --gen-fn ~/data/generation_functions.py --data ~/data/gsm8k_test.jsonl --out out/batch/kv2_shared.jsonl --kv-bits 2 --shared-scale
```

Аудит кэша:

```bash
HF_HUB_OFFLINE=1 python -m blockkv.audit_cache --data ~/data/gsm8k_test.jsonl --limit 20
```
